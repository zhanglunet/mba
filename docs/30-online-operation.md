# 30 — MBA 完全线上运行(零本机依赖)

> **用户决定(2026-07-27)**:免费社媒线**暂不接线**,先让 MBA **完全线上运行**。
> 本文记录:今天哪些事真的跑在云上、哪些**不在**、以及社媒线为什么被暂缓、什么时候值得开。
> 网页版:[mbabrand.com/runtime.html](https://mbabrand.com/runtime.html)。

## 1. 结论

**MBA 的日常运行 100% 在云端,不需要任何一台本机开着。**
每日舆情发现、预分类、入库、首页更新、站点部署、日报盘点、全部门禁 —— 都由 GitHub Actions
与 Cloudflare Pages 承担。关掉所有本地机器,系统照常出结果。

这不是新做的能力,是**既有事实**;本文把它写清楚,并明确"要不要为社媒线破这条规矩"是一个**取舍**,
而不是一个待办。

## 2. 云端跑什么

| 何时 | 干什么 | 产物 | 人工介入 |
|---|---|---|---|
| **每日 10:17(北京)** `watch-discover` | 五路召回(媒体 / 官方 / 官网直采 / 社区 / 自备 RSS)→ 候选 → LLM 预分类 → 折入 `events.yaml` → 重生成首页舆情条 → 开 PR | 舆情事件入库、首页「重大舆情」更新 | **无**(CI 绿后自动合并) |
| **每日 09:00(北京)** `daily-report` | 从 git 派生前一日工作盘点 | `docs/daily/<date>.md` | 补充说明人工补 |
| 手动触发 `watch-prescreen` | L1 便宜预筛:哪些品牌的新事件够格触发重审 | 预筛报告 | 读结论的人 |
| 每个 PR / push | `panel-validation` · `report-validation` · `mcp-ci` 全套门禁 | CI 红/绿 | 修红的人 |
| push 到 `main` | Cloudflare Pages 部署 | mbabrand.com | 无 |
| PR 改 `watch/_adopt/**` | triage 页提交的采纳自动折入 `events.yaml` | 事件流 | 审 diff 的人 |

三个出口也都在云上:**网站**(Cloudflare Pages)、**JSON API**(`site/api/*.json`,随站点静态发布)、
**MCP server**(npm 包)。

## 3. 哪些事**不**在云上(诚实边界)

1. **评委重审** —— FRESH / EVOLUTION 审计是人跑 Claude Code skill 发起的。
   这是设计如此:**审计分数从不自动变**,舆情只能"触发"重审的建议,不能自己改分。
2. **一手取数** —— `fetch_candidate draft/verify`、perspective 深化的原文抓取,
   需要能出网的会话(本机或本会话环境)。这些是**开发动作**,不是日常运行。
3. **自托管 RSSHub 社媒线** —— 见下。

前两条不影响"日常运行零本机依赖":它们是**人主动发起**的开发/审计动作,不是每日流水线的一环。

## 4. 社媒线为什么暂缓

管道、门禁、手册**全部就位**(`docs/16 §9.9` ① · `docs/27` · `docs/29`),2026-07-27 也已
**端到端实测打通**(公网侧代验:`/healthz` 200、微博路由 10 条真实条目、过 `parse_feed` 全部归一)。
唯一的问题不是技术:

> **它要求一台常开的机器。** RSSHub 跑在你的 Mac 上,隧道从你家出口连出去 ——
> 机器睡了、断网了、搬家了,当天这条源就没了。这与"完全线上、零本机依赖"**直接冲突**。

代价与收益摆在一起:

| | 完全线上(当前) | 加上本机社媒线 |
|---|---|---|
| 依赖 | 只依赖 GitHub + Cloudflare | 多一台必须 24×7 醒着的机器 |
| 失效模式 | 平台故障(罕见,且全网可见) | 机器睡眠 / 断网 / cookie 过期 / IP 被风控 —— **静默**,靠哨兵喊 |
| 拿到的信号 | 媒体 + 官方新闻室 + 官网直采 + 知乎 | **多出品牌官微一手发布** |
| 运维 | 0 | 升级镜像、换密钥、看哨兵 |

**当前选择:保持零本机依赖。** 这是取舍不是缺陷 —— 少一个信号源,换掉一整类静默失效。

## 5. 接线只需两步(想开的时候)

管道是**配置驱动**的,仓库侧零改动:

1. 建命名隧道 + 给容器配 `ACCESS_KEY`(全过程见 [`docs/29`](29-cloudflare-named-tunnel.md)),
   把密钥填进 GitHub Actions secret **`RSSHUB_KEY`**。
2. `site/reports-meta.yaml` 对应品牌加一行 —— **密钥写占位符,不写真值**(本仓库公开):

```yaml
    rss_feeds:
      - https://rsshub.mbabrand.com/weibo/user/<官微uid>?key=${RSSHUB_KEY}
```

次日 10:17 的自动发现就带微博信号。**先配 1~2 个品牌观察一周。**
护栏都在:`check_consistency` 拦明文密钥、变量没配时跳过并明确告警、自备 RSS 在社区名额里优先。

## 6. 什么时候值得开

不是"越多源越好",满足下面任一条再开:

- **某品牌的关键事件反复只在官微首发**,媒体转述滞后 24h 以上 —— 这时官微是真正的一手,值得为它破例。
- **你手上有一台本来就常开的机器**(小主机 / NAS / 常驻服务器),边际代价接近 0。
- 需要覆盖的品牌**本身没有英文新闻室**,官网也不被 Google News 索引(实测有这类品牌)。

反过来,如果只是"想多一个源",按第 4 节的账算,不划算。

## 7. 全线不变的边界

标题/日期/链接**逐字取自源**,不改写不翻译;`dim`/`severity`/`direction` 是
**model-judged 分类**并明确标注;**审计分数从不自动变** —— 舆情只能触发重审建议,
分数的每一次变化都来自评委重新 in-character 打分。
