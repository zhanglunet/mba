### 关键决策

- **官方源用 `site:` 而不是写抓取器**(#210):Google News RSS 支持 `site:` 语法,复用现有管道、
  **零新增抓取器**,URL 还直指官方原文。
- **必须锚到新闻室子域/路径,不能用根域名**:`site:apple.com` 召回 Apple Music 歌曲页、
  `site:tesla.com` 召回招聘页。改成 `apple.com/newsroom` / `news.microsoft.com` 才干净。
- **官网直采做通用提取,不写逐站选择器**(#212):"每站一套 CSS 选择器"最容易想到也最难维护
  (改版即静默失效,CI 不出网无法回归)。实测发现现代官网多是 Next.js/Nuxt、**数据以 JSON
  内嵌在页面里**,于是做成"抽内嵌 JSON → 自动找像新闻列表的对象数组"。换站/改版只要还是
  同框架就仍能跑。
- **静默失效必须做成哨兵**(#212/#214):配了源却抓到 0 条 = 站点改版/cookie 过期,而这类失效
  **不报错、只是不再有条目**。故 stderr + 候选 md 双告警。
- **免费社媒线:把计算挪到用户自己的机器**(#214):零运维的白嫖路全部实测排除(微博 API 返回
  访客系统 / RSSHub 公共实例 403 / freewechat 403 —— 都是**数据中心 IP 被拦**)。
  仓库侧只铺 `rss_feeds` 管道,用户本地 `docker run rsshub` 验证后填 URL 即开吃。
- **日变数字不能进门禁**(#209):原打算把「累计 858 条事件」纳入守卫,写之前意识到**它每天都变**,
  写死等于每天 CI 红。改成页面不写死、指向 `/watch/cockpit.html`。
  → **判断标准**:只有**变化频率远低于发布频率**的数字才适合写死 + 上门禁。
