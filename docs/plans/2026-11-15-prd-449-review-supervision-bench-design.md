# 评审监督台设计草稿（PRD-449/T1）

> 来源：trend issue [#2165](https://github.com/zhanglunet/trend/issues/2165)（[PRD-449/T1] 评审监督台设计）；PRD 全文：`zhanglunet/trend` 仓库 `adopted/PRD-449-mba-review-supervision-bench.md`。
> 状态：设计草稿（T1），只开 PR 不合并，等设计评审。
> 范围：本稿只写设计、接口、数据结构与验收标准，不写实现代码，不改本仓现有代码。

## 1. 问题与目标

评审结论一旦落账就进品牌审计报告。评委 agent 打分时，人今天只在评审复核收件箱里看到成品：这个分是怎么打出来的、哪路评委视角给了什么分、异常分有没有被解释，全都不可见。可疑评分要等到复核那一刻才被发现。

评审监督台的目标：每一次评分先过监督台再进下游。评分自带打分过程，人在台上随手批注、裁决，一键把反馈发回 agent，agent 改完再回来；未点头的评分不进品牌审计报告；批注与反馈全程留痕。

## 2. 设计要点

### 2.1 监督对象：一次评分

一次评分是监督台上的一行记录，包含：

- 评分标识：评分 ID、产生时间、评审任务标识、被评对象标识。
- 评分内容：各路评委视角的得分明细、汇总分、评分依据摘要。
- 打分过程：agent 依次走过的打分步骤（每路视角的评分理由、异常分的标注、汇总时的取舍），每一步带时间戳。
- 评分状态：见 2.3 的状态机。

打分过程是只读呈现：监督台展示过程，不重算分数、不改写 agent 的结论。

### 2.2 数据模型（三件套落账）

监督台落账三类记录，缺一不可：

1. **进度记录**：评分从出炉到裁决的每一步进展（出炉、被查看、被批注、被发回、被改回、被点头/被否决），每条带时间与操作人。
2. **批注记录**：人针对评分或其某一步打分留下的批注（文本、锚定的打分步骤、批注时间、批注人）。批注只附加，不覆盖评分原文。
3. **发回反馈记录**：人一点“发回”时产生的反馈单（反馈类型：重评 / 换评委包 / 补依据；反馈正文；关联的批注；发回时间）。agent 改完回来的新版本挂在同一次评分下，与旧版本并列可查，版本之间可逐项对照。

三类记录统一用评分 ID 串联；删除评分时三类记录一并归档，不单独抹除。

### 2.3 状态机与关口

评分状态流转：

```
出炉（draft）→ 待审（in-review）→ 已点头（approved）→ 进入品牌审计报告
                 ↓ 发回（sent-back）→ agent 改完 → 回到待审（in-review）
                 ↓ 否决（rejected）→ 归档，不进下游
```

关口规则（硬性）：

- 只有 `approved` 状态的评分可以进入品牌审计报告；评审复核收件箱只审人点头过的评分。
- `sent-back` 的评分在 agent 改完回来之前不得进入品牌审计报告；改回来的新版本重新走待审流程，不继承上一轮的点头。
- 否决的评分不进品牌审计报告，只留档备查。

### 2.4 监督接入点

agent 在三个时刻向监督台交数：

1. **评分出炉时**：提交评分内容 + 完整打分过程，状态为待审。
2. **agent 改完回来时**：提交新版本 + 本轮改了什么（对照上一轮的差异摘要），状态回到待审。
3. **状态变化时**：人的每次批注、裁决、发回都实时记入进度记录。

接入方式设计为“评分事件 + 查询接口”：agent 发事件上报，监督台提供按评分、按状态、按被评对象、按时间查询的只读接口；监督台不直接调用 agent 内部函数。

### 2.5 批注 / 裁决 / 一键发回回路

- **批注**：人在评分详情页对任意打分步骤或整次评分写批注；批注即时保存并对同一次评分的所有查看者可见。
- **裁决**：人在评分上做三选一裁决：点头 / 发回 / 否决。裁决必须带理由（点头可留空，默认“同意评分”；发回与否决必须写理由）。
- **一键发回**：点“发回”后，批注与反馈单自动打包成一条反馈消息发回 agent；agent 侧收到的是结构化反馈（类型 + 正文 + 关联批注），不是自由文本转发。

### 2.6 呈现：监督台一屏

一屏三区：左列是待审评分清单（按出炉时间倒序，标出每条的状态、被评对象与等待时长）；中区是当前评分的详情（评分内容 + 打分过程步骤）；右区是批注与反馈时间线。操作集中在中区底部：批注框、点头、发回、否决四个动作。

### 2.7 与既有模块的划界

- **不管报告评审（PRD-426）**：本台不管评审报告评审过没有，只管评分出炉的全程人看没看、批没批、agent 改没改。
- **不管结论真假（PRD-380）**：本台不验结论真假，只管监督流程本身。
- **不管待办收发（PRD-366）**：本台不管收件箱的待办收发，只管未点头的评分不进品牌审计报告。
- **不是协同会话**：人只批注和裁决，不下场改评分内容；改评分是 agent 的事。
- **不是事后审计链**：本台是事中监督 + 反馈回 agent，不是事后留痕；留痕是监督过程的副产品。

## 3. 接口草案

| 接口 | 方向 | 输入 | 输出 |
|---|---|---|---|
| 上报评分出炉 | agent → 监督台 | 评分内容 + 打分过程 | 评分 ID、初始状态 |
| 上报改回版本 | agent → 监督台 | 评分 ID + 新版本 + 差异摘要 | 新版本号、状态回到待审 |
| 提交批注 | 人 → 监督台 | 评分 ID + 锚定步骤 + 批注文本 | 批注 ID、时间戳 |
| 裁决 | 人 → 监督台 | 评分 ID + 裁决（点头/发回/否决）+ 理由 | 新状态 |
| 一键发回 | 人 → agent（经监督台） | 评分 ID + 反馈单 | 反馈已送达回执 |
| 查询评分清单 | 监督台 → 人 | 状态/被评对象/时间过滤 | 评分清单 |
| 查询评分详情 | 监督台 → 人 | 评分 ID | 评分 + 过程 + 批注 + 反馈时间线 |

所有接口只传业务字段，不传真实内部主机名、IP、账号或密钥；示例一律用占位符。

## 4. 验收标准

1. 一次评分从出炉到点头的全程（进度、批注、发回反馈）都能在监督台上查到，缺一类记录即不通过。
2. 未点头的评分无法进入品牌审计报告（以关口断言覆盖：待审、发回中、已否决三种状态各至少一条反例）。
3. 发回后 agent 改回的新版本重新待审，不继承上一轮点头。
4. 批注锚定到具体打分步骤可查；反馈单包含类型、正文与关联批注。
5. 设计评审通过（T1 本身的验收标准）。

## 5. 红线

- **评审监督台不碰分数、不碰评审流程。** 监督台只做呈现、批注、裁决与发回：不修改任何分数，不改动评委包与评审流程，不代行评审复核；分数的改动只能由 agent 在发回回路里完成、再回来重新待审。
- **未点头的评分不进品牌审计报告。** 这是本设计的硬关口，不设例外通道、不设绕过开关。
- **人只批注和裁决，不下场改评分。** 监督台不提供直接编辑评分内容的入口。
- **文档与示例中不得出现真实内部主机名、IP、账号或密钥，一律用占位符。**
- **实现类 PR 只开不合并，等用户 review。** 本稿是设计草稿，后续 T2–T5 的实现 PR 同样只开不合并。
