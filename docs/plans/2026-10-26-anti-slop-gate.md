# PRD-206/T1：反 AI 味评审门（slop gate）条目设计（草稿 v1）

> trend issue #1030。对应 PRD-206（中央仓库 zhanglunet/trend，`adopted/PRD-206-mba-anti-slop-review-gate.md`）。
>
> 定位：PRD-178 是"换人看"（消费者评委），本门是"换尺子量"——在 panel 评审与终审之间
> 加一道可执行的反 AI 味门：模板感、渐变滥用、空洞口号、构图雷同这类"AI 默认值"问题，
> Floor 级命中即拦截，不进终审。T1 只出条目设计（清单 + 分档 + 输出格式 + 破例留痕规格），
> 不写实现代码，不改评分业务逻辑（不动 5 镜头口径、meta_review 四项审计、
> PRD-177 findings 三态词表本身）。
>
> 依据（仓库现状，2026-10-26 实测）：① 现有评审流程 = 评委产出 `reviews/<slug>.md`
> → 聚合 `report.md`（Score Matrix / Dissent Heatmap）→ meta_review 一致性审计
> （`docs/plans/2026-10-18-meta-review-spec.md`，只出报告不改分）→ 终审；
> ② 评审结论的机读载体 = PRD-177 三态 findings.json（`docs/plans/2026-10-25-three-state-findings-json.md`，
> 状态词表 `confirmed / needs_validation / rejected`，findings_version = prd-177-v1），
> 本门的机读输出与之同级存放、词表对齐（见 §五）；
> ③ 关联 PRD-205（共享设计语言，T1 并行设计中）：本门条目以"编号引用"方式指向
> 设计语言条目（见 §七），不复制其内容。
>
> 借鉴：Nutlope/hallmark（MIT License）——只借鉴其三档分档形态
> （Floor 从不放行 / Reflex 可留痕破例 / Finish 永不拦截）与"破例须给理由并记录在案"的
> 治理思路；条目内容、编号、判定描述、正反例均为本仓库自研，未复制其条目文本。
> 原项目：<https://github.com/Nutlope/hallmark>。

## 一、门的位置与总则

流程（增量插入，不改既有环节职责）：

```
评委评审（reviews/*.md）→ 聚合 report.md → 【slop 门：本 PRD】→ meta_review / 终审
```

1. **门在终审之前**：门 verdict = `blocked` 时，该轮资产不进终审，退回改稿；
   改稿后重过门（新一轮 hits 重新判定，旧轮记录保留，见 §六留痕纪律）。
2. **门只量"AI 味"，不量对错**：分数高低、结论正误仍归 panel 与终审；门只回答
   "这份资产像不像机器默认值流水线出来的"。门不改分、不改评委结论。
3. **判定者**：由终审 Lead（或其指定的门执行人）在聚合后、终审前逐条核对本清单；
   T2 实现形态（脚本辅助/纯人工核对）不在 T1 范围，但每条判定描述都给可核查锚点，
   不允许"感觉像"式判定——命中必须能指出位置与证据（见 §五 hits 字段）。
4. **条目稳定性**：编号一经发布不复用、不重排；条目废弃时标记 `deprecated` 保留原文，
   不删除（与 findings 的 rejected 留痕纪律同款）。

## 二、分档定义（三档，借 hallmark 分档形态）

| 档 | 名称 | 命中后果 | 可否破例 |
|---|---|---|---|
| Floor | 拦截级 | 门 verdict = `blocked`，不进终审 | **不可破例**；只能改稿消除，或走误报复核（§六.3）推翻命中本身 |
| Reflex | 警告级 | 门 verdict 最高 `passed_with_warnings`；可进终审，但警告清单必须随终审材料全量呈现 | 可破例：按 §六填理由 + 审批，留痕后放行 |
| Finish | 提示级 | 只记录，不影响 verdict，不拦截、不需破例 | 不适用（无后果可豁免） |

分档判据（新条目入册时按此归档，避免随手定级）：

- **Floor**：命中即意味着"换个品牌名也成立"或"事实层面造假"——伤品牌资产可信度本身，
  不是品味问题。典型：整稿模板同构、无来源编造数字、与自家已审资产构图撞车。
- **Reflex**：是 AI 默认值指纹，但单看不致命、且存在正当例外（如品牌规范本身要求该形态）；
  允许有理由地存在，故必须留痕，不能静默放行。
- **Finish**：纯工艺细节，影响观感不影响可信度；只攒数据，为将来是否升档提供依据。

## 三、条目清单（四大类，编号 SLOP-<类>-<序号>）

类码：`T` 模板感（Template）/ `G` 渐变滥用（Gradient）/ `S` 空洞口号（Slogan）/ `C` 构图雷同（Composition）。
每条含：级别 / 判定描述（可核查锚点）/ 反例（命中）/ 正例（不命中）。
`design_refs` 为预留互引字段（§七），205 定版前统一记 `待对齐`。

### 3.1 模板感（T 类）

**SLOP-T-01（Reflex）默认组件套件原样出现**
- 判定：资产中出现 ≥2 种"模板零件"且未做品牌化改造：通用线性图标卡阵列、假浏览器框 /
  假代码窗装饰、通用头像占位 testimonial 块、每节标题上方统一小标签（eyebrow）等。
  锚点：逐个指出零件位置；"品牌化改造"指其形态/文案只能属于本品牌（换品牌即不成立）。
- 反例：落地页三段都是"图标 + 两行字"卡片，图标为通用线性图标，文案把品牌名换成
  `<competitor>` 仍然通顺。
- 正例：卡片结构相同，但每张卡的内容是该品牌独有的真实事件与数字，图标为品牌自有符号系统。
- design_refs：待对齐。

**SLOP-T-02（Floor）整稿换名测试不过**
- 判定：把整稿中的品牌名、产品名替换为任意竞品名后，全文仍然成立、无一处"只有本品牌
  才能说"的内容（具体事实、独有数据、特有结构任一皆可过关）。锚点：执行人实际做替换
  通读，并指出替换后仍成立的段落数；全文成立 = 命中。
- 反例：一篇品牌介绍通篇是"领先的 X 平台，致力于为用户创造价值"，换成任何同行名字毫无违和。
- 正例：文中含该品牌独有的创立事件、真实用户数据与产品机制描述，换名后多处事实性错误。
- design_refs：待对齐。

**SLOP-T-03（Finish）排版节奏全默认值**
- 判定：字号阶梯、段间距、行长全部落在通用模板默认档（如全篇同一级标题字号、
  区块间距等距），无一处有意打破节奏的设计决策。
- 反例：五个区块标题字号、间距、行长完全一致，像同一模板连灌五次。
- 正例：关键结论区放大字号并压缩行距制造停顿，其余区块保持常规节奏。
- design_refs：待对齐。

### 3.2 渐变滥用（G 类）

**SLOP-G-01（Floor）品牌色板外的高饱和多色渐变作主视觉**
- 判定：主视觉（首屏/封面）使用 ≥2 色相的高饱和渐变（如紫蓝、蓝绿 AI 默认渐变），
  且该渐变色不在品牌色板（PRD-205 设计语言色板条目）内。锚点：取渐变起止色与色板逐一比对，
  色板外 = 命中；品牌规范明文规定的渐变除外（须引规范条目编号，此时不命中）。
- 反例：封面是紫蓝渐变光晕，品牌色板里只有深灰与品牌橙。
- 正例：封面用品牌橙到深灰的同色系明度渐变，且色板条目明文收录该渐变。
- design_refs：待对齐（色板条目）。

**SLOP-G-02（Reflex）渐变无功能语义、纯装饰叠加**
- 判定：同一资产内 ≥2 处渐变既不表达层级/状态/数据，也不属于品牌规范，
  仅作背景装饰。锚点：逐处要求执行人写出该渐变的功能解释，写不出 = 计一处。
- 反例：标题底纹、正文卡片背景、页脚三处各有一层 unrelated 的彩色渐变，都说不出用途。
- 正例：仅热力图一处用渐变表达数据密度，其余界面元素纯色。
- design_refs：待对齐。

**SLOP-G-03（Finish）渐变参数全篇同一默认值**
- 判定：多处渐变方向与角度完全一致（如全是 135° 线性），显示未经设计、直接套默认参数。
- 反例：四处渐变全是同一角度同一方向，像复制粘贴。
- 正例：不同区块的渐变方向随版式走向分别设定，且与色板条目一致。
- design_refs：待对齐。

### 3.3 空洞口号（S 类）

**SLOP-S-01（Floor）标题级空洞断言**
- 判定：主标题 / 主口号是不可证伪的断言：无具体对象、无具体动作、无可核对事实，
  换任何品牌都成立。典型句式："重新定义 X""开启 X 新纪元""让 X 更美好"且全文无事实
  支撑该断言。锚点：执行人须写出"如何验证这句话为假"，写不出 = 不可证伪 = 命中。
- 反例：主标题"重新定义智能生活"，全文再无一句具体说明定义了什么。
- 正例：主标题"把合同审核从 3 天压到 4 小时"，后文给出流程与实测数据支撑。
- design_refs：待对齐（文案语气条目）。

**SLOP-S-02（Floor）无来源量化指标**
- 判定：资产中出现具体数字指标（提升 X%、服务 N 万用户、行业第一类排名断言），
  但无任何可追溯来源（内部数据须标口径与时间，外部数据须标出处）。锚点：逐个数字索要来源，
  索不到 = 命中一条（按指标计数，不按篇计数）。
- 反例："用户满意度提升 300%"，无调查口径、无时间、无出处。
- 正例："2026 年 Q2 内部工单统计：平均处理时长下降 31%（口径见附录）"。
- design_refs：待对齐。

**SLOP-S-03（Reflex）空转词堆叠**
- 判定：同一句/同一标题内出现 ≥3 个高频空转词（智能、赋能、生态、极致、引领、颠覆、
  革命性、全方位等，词表随条目版本维护），且该句无具体事实信息。锚点：计数 + 删词测试
  （删掉这些词后句子信息量不变 = 空转成立）。
- 反例："以智能科技赋能生态，引领极致体验"——删掉四个词后什么都没剩。
- 正例："给小商家用的记账工具，本月新增了发票识别"——无空转词，全是具体信息。
- design_refs：待对齐。

**SLOP-S-04（Finish）修辞密度过高**
- 判定：感叹句、排比句、四字短语连排在同一资产中高密度出现（执行人逐段计数，
  单段 ≥3 处计命中），呈现"口号墙"观感。
- 反例：一段里三组四字排比加两个感叹号，像发布会背景板文案。
- 正例：全篇仅主标题一处排比，其余为平实陈述。
- design_refs：待对齐。

### 3.4 构图雷同（C 类）

**SLOP-C-01（Floor）与已审资产构图同构**
- 判定：与本品牌已过审资产（或同批送审资产）骨架指纹一致：分区顺序、主视觉位置、
  卡片阵列形态三者全同。锚点：执行人做骨架指纹比对（只看结构不看内容），
  列出被比对资产路径与三项比对结果；三项全同 = 命中。
- 反例：本季度三份品牌页都是"大图 hero → 三卡片 → 数据条 → 评价 → CTA"同一顺序同一形态。
- 正例：新资产把数据条提前、取消卡片阵列改双栏叙事，骨架与既往资产可区分。
- design_refs：待对齐（版式条目）。

**SLOP-C-02（Reflex）无层级的等距阵列**
- 判定：全篇居中对齐 + 等高等距卡片阵列通到底，无一处大小/位置上的主次区分，
  读者无法一眼找到最重要的信息。锚点：执行人指出"最重要的信息在哪"，若结构上与
  次要信息同规格 = 命中。
- 反例：六张卡片一样大、一样间距，最核心的结论卡和凑数卡长得一模一样。
- 正例：结论卡跨两列放大，其余卡片常规规格，主次一眼可辨。
- design_refs：待对齐。

**SLOP-C-03（Reflex）主视觉缺席或不承载信息**
- 判定：首屏主视觉为通用图库式装饰图 / 抽象光效，与品牌核心信息无关，
  或首屏根本没有主视觉只有标题加按钮。锚点：遮住文案只看主视觉，能否说出"这是谁、
  干什么"；说不出 = 命中。
- 反例：首屏是一张蓝天白云通用图，遮住标题完全看不出是什么品牌。
- 正例：首屏主视觉是产品真实界面与真实使用场景，直接说明品牌在做什么。
- design_refs：待对齐。

**SLOP-C-04（Finish）留白节奏单一**
- 判定：所有区块边距/留白同一规格，无疏密变化，呈现模板灌装感。
- 反例：从头到尾每个区块上下边距分毫不差。
- 正例：结论区大留白制造停顿，明细区紧凑排列，节奏有意区分。
- design_refs：待对齐。

## 四、Floor 清单汇总（拦截线）

| 编号 | 条目 | 为什么是 Floor |
|---|---|---|
| SLOP-T-02 | 整稿换名测试不过 | 品牌资产的根基是"只有这个品牌能说"；整稿可替换 = 资产没有品牌专属性 |
| SLOP-G-01 | 色板外高饱和多色渐变作主视觉 | 与自有设计语言正面冲突，且是识别度最高的 AI 默认指纹 |
| SLOP-S-01 | 标题级空洞断言 | 主标题是资产的第一承诺；不可证伪 = 对读者的空头支票 |
| SLOP-S-02 | 无来源量化指标 | 事实层问题，不是品味问题；编造数字伤的是全部评审结论的可信度 |
| SLOP-C-01 | 与已审资产构图同构 | "千篇一律"的直接证据；同构资产重复发布等于自证流水线 |

其余 9 条：Reflex 5 条（T-01 / G-02 / S-03 / C-02 / C-03），Finish 4 条（T-03 / G-03 / S-04 / C-04）。
升降档纪律：条目升/降档须走条目变更流程（§九.3），不允许执行人临场改档；
Finish 条目攒够命中样本后是否升 Reflex，由 T5 回放报告的数据说话。

## 五、判定输出与 findings 三态衔接

### 5.1 机读输出：slop_gate.json（与 findings.json 同级同轮）

每品牌每轮评审一份：`published/reports/<brand>/versions/vN*/slop_gate.json`
（纯加法新文件，不改 report.md 与 findings.json 的既有字段）。

```json
{
  "gate_version": "prd-206-v1",
  "brand_slug": "example-brand",
  "report_ref": "published/reports/example-brand/versions/v1/report.md",
  "verdict": "blocked",
  "counts": {"floor": 1, "reflex": 1, "finish": 1, "exceptions": 0},
  "hits": [
    {"entry_id": "SLOP-G-01", "tier": "floor",
     "locus": "published/reports/example-brand/versions/v1/report.md#L12-18",
     "evidence_quote": "（占位：命中位置的原文/形态描述）",
     "note": "封面渐变起止色不在色板条目内（占位）"},
    {"entry_id": "SLOP-S-03", "tier": "reflex",
     "locus": "published/reports/example-brand/versions/v1/report.md#L30",
     "evidence_quote": "（占位：原句）",
     "note": "同句空转词 4 个，删词测试后无剩余信息（占位）",
     "exception_ref": null}
  ],
  "advisory": [
    {"entry_id": "SLOP-C-04", "tier": "finish",
     "locus": "published/reports/example-brand/versions/v1/report.md",
     "note": "全篇区块边距同一规格（占位）"}
  ],
  "exceptions": []
}
```

字段约束（T2 校验输入）：
- `gate_version` 固定 `prd-206-v1`，演进只加版本不改语义（沿 PRD-177 / PRD-151 的版本纪律）。
- `verdict` 三值：`blocked`（任一 Floor 命中且未被误报复核推翻）/ `passed_with_warnings`
  （无 Floor 拦截，有 Reflex 命中——含已破例与未破例）/ `passed`（无 Floor、无 Reflex）。
- `counts` 必须与 `hits` / `advisory` / `exceptions` 实际条数逐项一致（机判对账，沿 PRD-177 纪律）。
- 每条 hit 必有 `locus`（仓库相对路径 + 行锚或区块描述）与 `evidence_quote`（逐字引用或形态描述），
  **无证据不许命中**——这是防"感觉像"式误挡的第一道闸。
- Finish 命中只进 `advisory`，不进 `hits`，不参与 verdict 计算。

### 5.2 与 findings 三态的衔接（词表对齐，不改 177 schema）

本门**不直接写 findings.json**（findings 是评委结论的投影，门不是评委）；
衔接通过"同级文件 + 编号互引 + 终审引用"三件完成，语义对齐如下：

| 门的处置 | 语义 | 与三态的对应关系 |
|---|---|---|
| Floor 命中 → `blocked` | 该轮资产被门否决，不得进终审 | 终审 Lead 若就此下结论，落 findings 的 `rejected`，`rejected_reason` 须引门条目编号（如"slop 门 Floor 拦截：SLOP-S-02"），evidence 的 source_ref 指向 slop_gate.json 对应 hit |
| Reflex 命中（未破例） | 命中是事实，但处置未定：改稿消除或破例放行 | 语义对应 `needs_validation`：终审材料必须携带警告清单，不得只呈现已通过部分（沿 PRD-177 §四的计数透明化纪律） |
| Reflex 破例批准 | 命中事实不变，放行决定在案可查 | **不回写、不洗白**：hit 保留原文，`exception_ref` 指向 exceptions 记录；类比 findings 中 rejected 条目"保留不删除" |
| Finish 命中 | 仅数据积累 | 不进 findings，不进终审结论，只在回放（T5）时统计 |

衔接纪律：① `gate_version` 与 `findings_version` 各自独立演进，消费方遇未知版本拒读不猜；
② 终审报告引用门结论时必须渲染三档计数全量（floor / reflex / exceptions 都要出现），
不得只报"已通过"；③ evidence kind 枚举是否新增 `gate` 一类，由 PRD-177 后续版本决定，
本 T1 不擅改 177 的枚举（T3 互引落地时对齐）。

## 六、破例留痕机制（T4 的输入规格）

### 6.1 适用范围

- 只有 **Reflex 级**命中可破例。Floor 不可破例（hallmark 形态：Floor 从不放行）；
  Floor 命中只有两条出路：改稿消除，或误报复核（§6.3）推翻命中本身。
- 破例效力**只限本品牌、本轮、本资产**，不构成先例：下轮同条目同形态仍须重新申请。
  这防止"破一次例 = 条目事实废止"。

### 6.2 破例记录字段（slop_gate.json 的 exceptions[]，必填齐全才有效）

| 字段 | 说明 |
|---|---|
| `entry_id` | 被破例的条目编号（必须 ∈ 本轮 hits 中的 Reflex 条目） |
| `locus` | 命中位置，与对应 hit 一致 |
| `reason` | 理由，必填，两部分缺一不可：① 为什么这条在本资产上可接受（如品牌规范明文要求该形态、历史资产延续性）；② 依据引用（规范条目编号 / 已审资产路径等可核查出处）。**只有"我觉得没问题"不算理由** |
| `proposer` | 申请人（资产作者或送审人，仓库内可识别的身份标识，占位示例：`<proposer-id>`） |
| `approver` | 审批人：终审 Lead 或门条目维护人；**不得与 proposer 相同**（自批无效，沿 PRD-177 防"自己查自己"思路） |
| `date` | 批准日期（YYYY-MM-DD） |
| `scope` | 固定填 `single-round`（本轮有效）；跨轮复用须重新申请 |

无效破例（任一发生，破例视为不存在，verdict 按未破例计算）：字段缺失、`reason` 无依据引用、
`approver` == `proposer`、破例对象是 Floor 条目。T4 验收线"无理由破例不可放行"即按此判。

### 6.3 Floor 误报复核（与破例分开的第二条通道）

命中可能是门执行人的误判（如渐变其实在色板内、数字其实有出处未被看到）。
复核不是破例：它推翻的是"命中"这个事实判断，不是豁免它。

- 申请：送审方提交 `review_request`：条目编号 + "不适用/误判"的具体说明 + 反证引用。
- 复核人：门条目维护人（不得是原命中判定人）。
- 结论二值：`upheld`（维持命中）/ `overturned`（误报，命中撤销）。
- 留痕：结论写入该 hit 的 `review` 子字段（`{result, reviewer, date, note}`），
  hit 原文保留不删除；`overturned` 的 hit 不计入 counts 与 verdict，但回放（T5）统计误报率时要算它。
- 复核只有一次：`upheld` 后不得就同一 hit 重复申请（防缠讼）；改稿后重新送审是新一轮，不受此限。

### 6.4 呈现纪律

终审报告与任何对外汇总引用门结论时，破例记录必须**全量渲染**（条目、理由摘要、审批人），
不得只渲染"已放行"而隐去破例明细——与 PRD-177"不得只渲染 confirmed 而隐去 rejected"同款纪律。

## 七、与 PRD-205 设计语言的互引机制（T3 的输入规格）

1. **只引编号，不抄内容**：每条 slop 条目预留 `design_refs` 字段，值为设计语言条目编号列表。
   预期编号形态为 `DL-<域>-<序号>`（如色板、版式、文案语气等域）——**此形态为假定，
   以 PRD-205 定版文档的编号方案为准**。本 T1 写作时（2026-10-26），PRD-205 文档
   （`docs/plans/2026-10-26-design-language-spec.md`）尚未落地 main，故 §三各条目
   `design_refs` 一律记"待对齐"，不杜撰 205 的具体编号。
2. **对齐动作（T3 执行）**：205 定版后，按其编号表逐条回填 `design_refs`；
   回填是一次独立变更，须在变更说明中列出"条目 ↔ DL 编号"对照全表。
3. **互引校验规则（T3 落地）**：
   - 悬空引用报错：`design_refs` 中的编号必须在 205 条目表中真实存在（机判，同 findings R-4 思路）；
   - 冲突检查：若某 DL 条目的"正例"形态恰好被某 slop 条目判为命中（如 205 推荐的某种
     渐变用法撞上 SLOP-G-02），不许门或设计语言任何一方单方面改口径消解——登记为
     **互引冲突**，提交两 PRD 维护人裁决，裁决结论回写两边文档的变更记录；
   - 反向引用：建议 205 条目在"误用提示"处反引 slop 编号（是否采纳由 205 维护人定，
     本 PRD 只提接口，不替对方定内容）。
4. **版本关系**：slop 条目引用的是 DL 编号而非其文本快照；205 条目改义（非改字）时，
   须通知门维护人复评引用它的 slop 条目是否还成立，复评结论记入条目变更记录。

## 八、与 livead PRD-193 门的口径对照约定

PRD 风险条已点名：两仓门条目若各自演化，同一形态在 mba 判 Floor、在 livead 判警告，
口径漂移会让两边的评审结论不可比。本节定对照约定（T1 只定约定，对照表实体由后续任务维护）：

1. **对照维度**：按概念不按编号——四大类（模板感 / 渐变滥用 / 空洞口号 / 构图雷同）是
   两仓共用的概念框架；对照表逐行列"概念条目 ↔ mba 编号 ↔ livead 编号 ↔ 两边级别"，
   任一侧无对应条目时显式记 `无对应`，不许留空假装对齐。
2. **触发节奏**：任一仓门条目发生增 / 删 / 改级 / 改判定描述时，触发一次对照；
   此外每季度至少做一次例行对照（无变更也要留"已对照、无漂移"的记录行）。
3. **漂移分类与处置**：
   - **有意差异**：源于域差异（如 livead 的投放素材有时效性构图惯例）——登记备案，
     注明差异理由，两边各自保留，不算漂移；
   - **无意漂移**：同一概念两边判定/级别不一致且无域理由——对齐到**较严**一侧，
     或共同上收为 trend 层共识条目，二选一，不许长期双轨；
   - **争议**：对齐方向谈不拢——升级用户裁决，对照表记 `待裁决` 并冻结争议条目的改动。
4. **记录落点**：对照纪要两仓各存一份（各自 `docs/plans/` 下，文件名含日期），
   内容一致；纪要须含对照日期、双方门版本（gate_version）、漂移条数与分类统计。

## 九、非目标与边界

1. 不替代终审与 PRD-178 消费者评委：门只拦"AI 味"，不评品牌好坏、不评消费者观感。
2. 不做生成侧改造：门只在评审侧判定，不规定资产该怎么写（那是 PRD-205 设计语言的事，
   两者分工：205 给"应该长什么样"，206 查"不该长什么样"）。
3. 条目变更流程（升降档/新增/废弃）走文档 PR + 评审，不在本 T1 展开流程细节；
   但底线先定：编号不复用、废弃保留原文、改级须在变更说明中给出命中数据或案例依据。
4. 文档与示例中不出现真实内部主机名 / IP / 账号 / 密钥；示例身份一律占位符。
